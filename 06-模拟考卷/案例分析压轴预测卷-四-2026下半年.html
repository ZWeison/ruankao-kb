【问题 1】参考答案（9 分）

（1）三阶段职责（3 分，每个 1 分）：

  • Try（预留）：检查业务并预留必要资源（如冻结库存数量、预占账户额度），不真正完成业务；
  • Confirm（确认）：真正执行业务，使用 Try 预留的资源完成操作，要求成功（失败则重试）；
  • Cancel（取消）：取消 Try 阶段的预留，释放资源，使数据回到初始状态。

（2）比较（6 分，每方面 2 分）：

  • 补偿方式：TCC 的 Try/Confirm/Cancel 由业务显式实现三个接口，Cancel 对 Try 做反向补偿；Saga 将长事务拆为一系列本地事务 T1…Tn，每个 Ti 配置补偿事务 Ci，失败时逆向依次执行 C(i-1)…C1，无资源预留阶段（每个本地事务直接提交）。
  • 隔离性：TCC 通过 Try 预留使中间状态对外不可见，隔离性较好；Saga 中间状态直接可见，存在脏读与其他事务覆盖的风险，需要业务侧增加约束（如状态机、业务规则容忍）。
  • 适用场景：TCC 适合短事务、参与方少、一致性要求高的核心链路（如资金），但开发成本高；Saga 适合流程长、参与方多、能接受最终一致的长事务场景（如跨系统业务流程），开发量相对小。

【问题 2】参考答案（8 分）

（1）主要步骤（5 分）：

  • ① 订单服务在同一个本地事务中写业务表和本地消息表（消息状态为"待发送"），保证业务与消息的原子性；
  • ② 消息投递组件（中继任务）扫描本地消息表，将待发送消息投递到消息中间件；
  • ③ 下游服务（库存/结算/积分）消费消息，执行本地事务并返回消费回执（ACK）；
  • ④ 上游收到回执后将消息状态更新为"已完成"；
  • ⑤ 定时任务对长时间"待发送/未确认"的消息重试投递，并对账补偿，从而保证消息不丢、双方最终一致。

（2）死信队列作用（3 分）：多次消费失败或超时未确认的消息转入死信队列，避免反复重试阻塞正常消费；对死信消息进行告警、人工排查、对账与补偿处理，保证消息不丢不漏，是最终一致性的兜底机制。

【问题 3】参考答案（8 分）

（1）（6 分，每个含义 1 分、方法 1 分）：

  • 幂等：同一操作执行一次与多次的效果相同。解决：以唯一业务键建去重表／唯一索引，或用状态机条件更新，重复请求直接返回上次结果。
  • 空回滚：Try 未执行（如网络超时未到达）而 Cancel 先到达，此时没有可释放的预留资源。解决：记录事务执行表，Cancel 时若查不到 Try 记录，则登记"已空回滚"并直接返回成功。
  • 悬挂：Cancel 先执行完成之后，迟到的 Try 才到达并预留资源，该资源将永远无人释放。解决：Try 执行前先检查事务执行表，若发现事务已回滚（空回滚标记）则拒绝执行 Try。

（2）（2 分，任答两点）：① 按业务单号建唯一索引／去重表判重；② 使用版本号或状态机做条件更新，仅当状态合法时生效；③ 消费记录 Redis 缓存判重（SetNX）。答出其中两种即可。

【问题 1】参考答案（9 分）

（1）（6 分，每方面 2 分）：

  • 存储开销：3 副本冗余 200%（有效容量仅 1/3）；EC 8+3 冗余 37.5%（有效容量 8/11），开销显著更低。
  • 可靠性：3 副本可容忍任意 2 个副本同时丢失；EC 8+3 中 8 个数据块加 3 个校验块，可容忍任意 3 块（所在盘/节点）同时故障，且故障域可按机架/节点分布扩展。
  • 读写性能：副本写路径简单、可就近读取，读性能好；EC 写入需计算校验块（CPU 开销），部分读或降级读需多块重构，性能与延迟更高。

（2）（3 分）：

EC 8+3 存 8 份有效数据需 11 份物理空间，容量开销 = 11/8 = 1.375
3 副本开销 = 3.0
开销之比 = 1.375 / 3.0 ≈ 0.46（节省约 54% 空间）

可容忍的最大同时故障盘数为 3。

【问题 2】参考答案（8 分）

（1）（6 分，每方面 2 分）：

  • 元数据组织：对象存储采用扁平化命名空间（桶 + 对象键）和集中/分布式的 KV 元数据服务，文件存储为树形目录结构；
  • 访问方式：对象存储通过 RESTful HTTP 接口（PUT/GET/DELETE 按 Key 访问），不提供 POSIX 语义；文件存储通过 NFS/CIFS 挂载，支持随机读写与文件锁；
  • 扩展性：对象存储的数据节点与元数据服务均可水平扩展，容量可扩展至 EB 级、对象数十亿级；文件存储在元数据规模和目录深度上易成瓶颈，扩展性受限。

（2）（2 分）：按数据的访问频度与时效自动在热（SSD+副本）、冷（HDD+EC）、归档层之间迁移、降冗余或清理过期数据，在保证可访问性的前提下显著降低存储成本，无需人工干预。

【问题 3】参考答案（8 分）

（1）（6 分，过程 4 分、结果 2 分）：

冷数据：5PB × 80% = 4PB；EC 8+3 裸容量 = 4PB × 11/8 = 5.5PB
热数据：5PB × 20% = 1PB；3 副本裸容量 = 1PB × 3 = 3PB
合计裸容量 ≈ 5.5 + 3 = 8.5PB

（工程实施还应预留 20%～30% 余量用于系统开销、修复流量与扩容缓冲。）

（2）（2 分）：EC 8+3 任意 3 块故障可重构数据、3 副本任意 2 个副本丢失可恢复，单节点故障均不会丢数据，满足要求。元数据服务应采用集群化部署（多节点 + 分布式 KV 存储 / Raft 等共识协议保证强一致与自动选主），并对元数据做冗余与定期备份，消除单点。

【问题 1】参考答案（9 分）

（1）（4 分）：横向联邦：各参与方特征空间相同（或相近）、样本 ID 不同，即"样本切分"，训练时按特征对齐；纵向联邦：各参与方样本 ID 重叠较多、特征空间不同，即"特征切分"，需先通过加密样本对齐（PSI）求交，再交换中间加密结果。

（2）（5 分）：判断：应采用横向联邦（2 分）。理由：各市场方的业务字段与特征体系基本一致，但各自商户样本互不相同，属于典型的"特征对齐、样本切分"场景，无需跨方样本求交（3 分）。

【问题 2】参考答案（8 分）

（1）（4 分）：作用：使参数服务器只能获得各参与方梯度聚合后的总和，无法还原任一参与方的个体梯度，防止从模型更新反推原始数据（2 分）。实现技术（任答两种，2 分）：同态加密（在密文上直接求和）、秘密共享（各方将梯度拆分份额、份额求和重构聚合值）、成对随机掩码（Bonawitz 掩码抵消）。

（2）（4 分）：作用：对上传的梯度注入满足 ε-差分隐私的随机噪声，使攻击者无法以高置信度判断某个体样本是否参与训练，提供可量化、可证明的隐私保障（2 分）。代价：噪声引入精度损失，需要在隐私预算 ε 与模型效用之间权衡；噪声与聚合还会增加计算与通信开销（2 分）。

【问题 3】参考答案（8 分）

  • （1）Non-IID　问题：各方数据分布差异大（标签/特征分布不同），聚合后的全局模型在部分参与方上精度下降（2 分）。对策：个性化联邦（全局模型 + 本地微调）、分层/加权聚合、数据增强与重采样、联邦迁移学习。
  • （2）通信开销　问题：参与方多、模型大、通信轮次多，通信成为瓶颈（2 分）。对策：梯度压缩（量化/稀疏、Top-K 上传）、本地多轮训练减少通信轮次、异步聚合、就近部署参数服务器。
  • （3）投毒攻击　问题：恶意参与方上传毒化梯度使全局模型被污染（后门/精度劣化）（2 分）。对策：鲁棒聚合算法（Krum、Trimmed Mean、中位数聚合）、梯度异常检测、参与方准入与信誉评估、数据与模型审计。
  • （4）数据合规　要求：个人信息处理需取得同意并最小化采集，重要数据出境需安全评估，全过程可审计（2 分）。措施：原始数据不出域、传输与梯度全程加密、脱敏与去标识化、留存联邦训练审计日志、明确各方数据处理协议。

【问题 1】参考答案（9 分）

（1）（4 分）：本体是领域概念及其关系的形式化、规范化的定义（图谱的模式层）。作用：统一语义与建模口径、约束图谱结构、支撑推理与知识复用（2 分）。建模要素：类（概念）、属性（数据属性/对象属性）、关系（实体间关联）、公理/约束、实例（2 分，答出 4 个即可）。

（2）（5 分）：实体识别（NER）：从非结构化文本中识别实体 Mention 并标注类别（商户、商品、市场、时间等），方法如规则词典、CRF 序列标注、BERT+CRF 预训练模型微调（2.5 分）；关系抽取（RE）：判定实体对之间的语义关系（如"供应""检出""处罚"），方法如基于依存句法的规则模板、远程监督、预训练模型分类（2.5 分）。

【问题 2】参考答案（8 分）

（1）（4 分）：关系数据库实现多跳关联需多次 JOIN，代价随跳数与数据量急剧增长；图数据库以图结构原生存储，遍历通过邻接指针完成（无索引邻接、免 JOIN），深层关联查询性能稳定，且图模型与业务语义直观匹配，适合追溯、传导类分析。

（2）（4 分）：属性图由节点（实体，可带标签与属性）、边（有向关系，带类型与属性）、属性（键值对）组成。示例：节点（商户：甲公司 {信用等级：A}）通过边（：供应 {数量：200，日期：2026-08-09}）指向节点（商品：冷鲜猪肉 {产地：XX}）。

【问题 3】参考答案（8 分）

（1）（4 分）：实体对齐：将不同数据源中指向同一真实实体的记录链接为图谱中同一节点（如"永辉超市"与"永辉超商"），保证实体唯一性；冲突消解：同一实体的同一属性在多来源取值不一致时，依据来源可信度、数据时间戳、权威程度等策略选择或标记待复核值，保证知识一致可信。

（2）（4 分）：增量更新：通过 CDC/消息订阅捕获源系统变化，进入"抽取—融合—入库"流水线，数据模型与数据版本化管理（按"变更日志"），支持回滚（2 分）。质量控制：入库前 Schema 与值域校验、置信度阈值过滤低质量三元组、抽样人工复核、问题反馈闭环修正，并定期全量对账评估（2 分）。
