# 试题一（必答题，25分）订单计价模块重构

阅读以下关于面向对象建模与设计模式应用的叙述，在答题纸上回答问题 1 至问题 3。

某电商平台对其**订单计价模块**进行重构。原有代码在 **OrderService** 中以大量 if-else 分支硬编码折扣逻辑（按比例打折、固定金额减免、会员专享等），每新增一种营销方式都需要修改并回归整个服务。重构后，计价上下文 **OrderContext** 依赖折扣计算抽象接口 **DiscountStrategy**，各折扣算法实现为独立类，运行时注入；订单生命周期由订单状态机统一管理。架构师给出了计价模块的类图（图 1-1）与订单状态图（图 1-2）。

```text

│ - strategy: DiscountStrategy   │──strategy─▶│ DiscountStrategy            │
│ + setStrategy(s: DiscountStrategy)        │ + discount(amount: double): double │
│ + calcTotal(amt: double): double│          └──────────────┬───────────────┘
└────────────────────────────────┘                         △ 实现
                                    ┌──────────────────────┴──────────────────────┐
                                    │                                             │
```

# 试题二（选答题，25分）订单库分库分表改造

阅读以下关于数据库分库分表架构设计的叙述，在答题纸上回答问题 1 至问题 3。

## 【说明】

某电商平台的订单库为单实例 MySQL，订单表约 **8 亿行**，数据文件超过 **2 TB**。近一年出现明显瓶颈：高峰写入 TPS 达 **3 万**，磁盘 IO 频繁饱和，大表加索引需要锁表数小时；历史数据归档后单表仍有数亿行，复杂查询性能急剧下降。DBA 与架构师决定实施分库分表改造：按业务先行**垂直拆分**，再对订单表按**水平分片**拆到 4 个分片库，每个分片库承载 2 亿行以内，并引入分片中间件统一路由，如图 2-1 所示。平台对"我的订单"查询频率远高于其他查询，且必须保证改造期间业务连续。

**图 2-1　订单库分片架构**

```text
   订单服务        报表服务
      │              │
      ▼              ▼
 ┌──────────────────────────────────┐   ── 取号 ──▶  ┌──────────────────┐
 │ 分片中间件                        │               │ 全局 ID 生成器    │
 │ SQL 路由 / 改写 / 结果归并        │               │ 发号服务          │
 └───────────────┬──────────────────┘               └──────────────────┘
                 │
    ┌────────┬───┴────┬────────┬────────┐
    ▼        ▼        ▼        ▼
 ┌───────┐┌───────┐┌───────┐┌───────┐
 │分片 0 ││分片 1 ││分片 2 ││分片 3 │
 │user_id││user_id││user_id││user_id│
 │%4 = 0 ││%4 = 1 ││%4 = 2 ││%4 = 3 │
 └───────┘└───────┘└───────┘└───────┘
```

## 【问题1】（9 分）

（1）说明垂直拆分与水平拆分各自解决什么问题及适用场景。（3 分）

（2）结合本案例说明水平分片键的选择原则，并分析订单表分片键选 **user_id** 而非 **order_id** 的理由。（3 分）

（3）比较范围分片、哈希取模分片、一致性哈希分片在**数据分布均匀性**、**扩容代价**、**热点风险**三方面的差异。（3 分）

## 【问题2】（8 分）

（1）分片后，"按商品维度统计近 30 天销量"这类跨分片聚合查询的执行存在什么困难？给出至少两种解决思路。（3 分）

（2）说明雪花（Snowflake）算法生成全局唯一订单号的原理，并指出其两个注意点。（3 分）

（3）说明从 4 个分片扩容到 8 个分片时，可采取的数据迁移方案要点。（2 分）

## 【问题3】（8 分）

（1）说明跨分片"深分页"查询（如 `ORDER BY create_time LIMIT 1000000, 20`）性能差的原因，并给出两种优化方案。（4 分）

（2）平台存在少量年销售额上亿的"大商户"，按 user_id 哈希后其数据集中落于单一分片，形成数据倾斜与热点。请给出治理思路（至少两条）。（4 分）

# 参考答案与解析

> 全卷 15 小题、满分 125 分。参考答案按题号归集在文末，建议**答完一题不急着看**，整卷做完再统一对照，避免边看边抄。

## 试题一　参考答案与解析

### 问题1（9 分）

**（1）设计模式识别（5 分）**

- 采用**策略模式（Strategy）**。（1 分）
- **意图：**定义一系列算法，把它们一个个封装起来，并且使它们可以互相替换；使得算法的变化独立于使用算法的客户。结合本案例：折扣算法可独立于计价上下文变化与扩展。（2 分）
- **角色：**`DiscountStrategy` 为策略接口（Strategy）；`PercentagDiscount`、`FixedDiscount` 为具体策略（ConcreteStrategy）；`OrderContext` 为环境类（Context），持有策略引用并把计算委托给策略对象。（2 分）

**（2）新增算法与开闭原则（4 分）**

- **实现：**分别为"满减优惠""会员折扣"新建类实现 DiscountStrategy 接口，在运行时通过 setStrategy 注入或经配置/工厂选择即可，OrderContext 与既有算法类均不改动。（2.5 分）
- **开闭原则体现：**对扩展开放——新增算法只需增加新的具体策略类；对修改关闭——无需修改环境类与既有策略类源码，避免了 if-else 分支的持续膨胀，降低回归风险。（1.5 分）

### 问题2（8 分）

**（1）状态图要素与未定义事件处理（3 分）**

- **要素：**状态（含初始态、终态）、事件（触发转换的激励）、转换（状态间因事件发生的迁移），以及可附在状态上的活动/动作。图 1-2 中"待支付、已支付、已发货、已完成、已取消、退款中、已退款"为状态，"支付成功、发货、确认收货、取消订单、申请退款、退款完成"等为触发事件。（2 分）

## 试题二　参考答案与解析

### 问题1（9 分）

**（1）垂直拆分与水平拆分（3 分）**

- **垂直拆分：**按业务边界把不同表拆到不同库（库级垂直），或按访问频度把宽表字段冷热分离（表级垂直）。解决单库表多、单表过宽、业务耦合的问题；适用于业务边界清晰、表间耦合低的场景。（1.5 分）
- **水平拆分：**按行依据分片键把一张表的数据分散到多个库表。解决单表数据量与并发量过大、索引与锁开销高的问题；适用于单表数据量巨大的场景（本案例 8 亿行）。（1.5 分）

**（2）分片键选择与 user_id 的理由（3 分）**

- **分片键选择原则：**基数高、数据分布均匀、绝大多数高频查询都携带该字段、业务上取值稳定不改。（1.5 分）
- **本案例理由：**"我的订单"（按 user_id 查询）频率最高；用 user_id 分片可使同一用户的全部订单落在同一分片内，路由为单分片查询，避免跨分片扫描与归并。若按 order_id 分片，"我的订单"需广播到全部分片，代价高。order_id 详情查询可通过"order_id 中编码分片位"或引入映射表解决。（1.5 分）

**（3）三种分片算法比较（3 分）**

| 算法 | 数据分布均匀性 | 扩容代价 | 热点风险 |
|---|---|---|---|
| 范围分片 | 按分片键区间划分，可能不均 | 低：只需追加新区间、迁移少 | 高：访问若随时间递增会形成写入热点 |
| 哈希取模 | 均匀 | 高：取模数变化需大规模数据迁移，期间路由复杂 | 低（但倾斜字段仍会热点） |
| 一致性哈希 | 较均匀 | 小：节点增减仅影响相邻区间 | 中：实现复杂，虚拟节点配置不当时仍可能倾斜 |

### 问题2（8 分）

**（1）跨分片聚合的困难与思路（3 分）**

- **困难：**满足条件的数据分散在 4 个分片，需各分片局部聚合后再归并，网络与内存开销大，且分页、排序语义难以正确实现。（1 分）
- **思路（答出两条即可，2 分）：**①索引/宽表——经 binlog 同步构建 ES 或汇总表，统计类查询走检索层；②预聚合——按天/按商品汇总到结果表；③字段冗余——把常用维度（商品、类目）冗余进订单表，减少跨库关联。

**（2）雪花算法（3 分）**

- **原理：**64 位整数 = 1 位符号位 + 41 位时间戳（毫秒）+ 10 位机器标识 + 12 位序列号，单机每毫秒可生成 4096 个趋势递增的全局唯一 ID。（2 分）
- **注意点（答出两点，1 分）：**①依赖机器时钟，时钟回拨会导致重复 ID，需回拨检测与等待/备用位处理；②机器标识需分配机制保证全局唯一；③强依赖时间意味着 ID 泄漏业务量信息（可按需评估）。

**（3）扩容迁移要点（2 分）**

方案：双写/增量同步（CDC、binlog 监听）先建新分片 → 存量数据按新规则批量迁移 → 一致性比对（总量、抽样、校验和）→ 灰度读（灰度比例放量）→ 观察稳定后切写并下线旧路由；迁移期间以旧路由为回滚，保证业务连续。

### 问题3（8 分）

**（1）深分页原因与优化（4 分）**

- **原因：**全局有序需各分片都返回前 offset+limit 条记录到中间件，在内存中归并排序后再丢弃前 100 万条——各分片传输与排序的数据量巨大，页越深代价越高，且可能拖垮中间件内存。（2 分）
- **方案（答出两种，2 分）：**①游标（seek）分页——以 `WHERE create_time > 上次末尾值 ORDER BY create_time LIMIT 20` 替代 offset；②限制最大翻页深度并引导走检索层（ES）；③"二次查询"折中法（先取区间再重排，减少归并量）。

**（2）热点与大商户治理（4 分，答出两条、每条 2 分）**

- **复合分片键：**分片键由 user_id 叠加二维维度（如月份、店铺子账号），把大商户数据打散；
- **热点单列路由：**对识别出的热点商户建立映射表落到独立分片/独立实例，与其用户隔离；
- **写缓冲：**热写入先入消息队列/内存缓冲再异步落库，削峰填谷；
- **业务手段：**把大商户迁移为独立租户库，或对其报表类需求走离线/异库索引，减少在线分片压力。

### 问题1（9 分）

**（1）四种演化策略与选择（5 分）**

| 策略 | 适用情形（业务价值 / 技术条件） |
|---|---|
| 淘汰 | 业务价值低、技术条件差，且其功能可被其他系统替代——直接废弃 |
| 继承 | 业务价值高、技术条件稳定，只需少量维护——作为资产保留并封装接口供其他系统调用 |
| 改造 | 业务价值高、技术条件落后——通过重构、再工程提升其架构与技术水平 |
| 集成 | 自身价值有限但需与其他系统协同——通过接口/总线把它纳入整体环境 |

（每点 0.5 分，共 2 分）

- **本案例应采取"改造"策略**（1 分）：核心业务规则仍有效、业务价值高，但技术栈陈旧、供应商失联、安全难保障，属"技术条件差"，须提升技术水平而非简单淘汰或仅做集成。（2 分）

**（2）三种转换方式与选择（4 分）**

- **直接转换：**某时点旧停新启，成本低、周期短，但风险最高，适合小规模/非关键系统；
- **并行转换：**新旧系统并行运行一段时间、结果互校，风险最低，但人力与资源成本翻倍；
- **分段转换：**按子系统/分支机构分批切换，风险与成本居中，便于逐步验证与回退；（每点 1 分，共 3 分）
- **本案例选择分段转换**（1 分）：公积金核心业务中断不可接受，且功能模块（归集、提取、贷款、渠道）边界清晰，宜按模块分批切换，关键模块辅以短时并行核对。

### 问题2（8 分）

**（1）绞杀者模式（4 分）**

- **原理：**在遗留系统外围新建门面/路由层，新功能以新服务实现并逐步接管旧功能流量，旧系统被"缠绕"并逐渐萎缩，最终安全下线；而非一次性重写替换。（2 分）
- **步骤：**①新建统一入口/门面层并接管流量；②识别高价值功能优先新建为服务并路由切流；③按功能逐步迁移、灰度放量并保留回退能力；④旧系统功能清空后下线。（1 分）
- **适合本案例的原因：**核心业务不能中断、老系统规模巨大（90 万行）难以一次性重写，绞杀者允许按模块渐进替换、随时回退，历史数据可在迁移完成后下线。（1 分）

**（2）防腐层（4 分）**

- **做法：**在新旧系统交界处建立独立的适配层，对新系统屏蔽老系统的表结构、协议与领域模型，把遗留模型转换为新系统的领域模型后再进入新系统。（2 分）
- **作用：**防止遗留模型的概念、脏数据与历史包袱渗入新设计，保证新系统模型的干净与可演化；同时集中管理对老系统的访问，为老系统下线时替换适配（数据源切到新库）提供唯一改动点。（2 分）

### 问题3（8 分）

**（1）数据迁移步骤与双写方案（4 分）**

- **步骤（2 分）：**①数据范围评估与清洗（去除冗余、修复异常）；②字段映射与转换规则设计；③存量全量迁移（先演练再正式）；④增量同步（双写或 CDC 捕获增量）；⑤一致性比对（总量、金额汇总、抽样、校验和）；⑥灰度切换与观察；⑦保留回滚窗口后下线老库。
- **各步作用（2 分）：****双写**保证迁移窗口内旧库增量不丢；**比对**证明迁移正确、可量化验收；**灰度切换**按比例把读写流量切到新库，异常时立即切回，**回滚窗口**兜底。

**（2）逆向工程、重构、再工程（4 分）**

- **逆向工程：**分析已有系统以识别其构件及其相互关系，恢复设计信息与架构，在更高抽象层次上建立系统表示；不改变系统本身。（1.5 分）
- **重构：**在不改变软件外部行为的前提下，调整其内部结构以改善可理解性与可修改性。（1 分）
- **再工程：**在逆向工程获取设计信息的基础上，对系统进行重构并按新需求重建（改变功能的形式或实现方式），提升质量。（1.5 分）
- **关系：**逆向工程"由代码到设计"，前向工程"由设计到代码"，再工程 = 逆向工程 + 重构 + 前向工程；本案例梳理老系统业务规则即逆向工程的应用。

## 试题五　参考答案与解析

### 问题1（9 分）

**（1）FaaS 与 BaaS（4 分）**

- **FaaS（函数即服务）：**开发者以函数为单位部署业务逻辑，平台负责函数的运行环境、弹性实例调度与执行计费，事件触发执行、执行完即释放；开发者不管理服务器。（2 分）
- **BaaS（后端即服务）：**数据库、对象存储、消息、认证等后端能力以云服务形式提供，由云厂商承担，应用以 API/SDK 直接使用。（1 分）
- **组合原理：**计算交给 FaaS、状态与通用能力交给 BaaS，开发者只写业务函数，实现"无服务器"——服务器存在但对开发者透明。（1 分）

**（2）与容器化常驻服务比较（5 分，每方面约 1 分）**

| 方面 | 容器化常驻服务 | Serverless（FaaS） |
|---|---|---|
| 资源管理 | 需规划并维护实例规格与副本数 | 无须管理实例，平台按请求自动分配与回收运行环境 |
| 计费方式 | 按资源占用时长计费，闲置也付费 | 按请求次数与执行时长（GB·秒）计费，闲置零成本 |
| 伸缩方式 | 需配置 HPA/事件驱动伸缩，有一定滞后，须预留余量 | 平台秒级至实例级并发伸缩，可应对突发流量 |
| 运行时长限制 | 可长期运行 | 单次执行有最大时长与内存/临时磁盘限制，超时需拆分或改用异步/工作流 |

### 问题2（8 分）

**（1）冷启动及缓解（4 分）**

- **成因（1.5 分）：**函数被调用时才拉起运行环境——申请资源、拉容器/微虚拟机、加载运行时与函数代码、初始化依赖（连接、SDK、模型），首请求时延显著高于热请求。
- **缓解措施（2.5 分，答出三种）：**①预热——定时触发空跑、预留实例/预置并发，保持最小热实例池；②精简依赖与包体、延迟初始化（首次调用再建连接）、复用执行上下文与全局连接；③选择轻量运行时或更快的恢复技术；④对时延敏感链路改用常驻容器与 FaaS 混合部署。

**（2）无状态约束的问题与解决（4 分）**

- **问题（2 分）：**实例随时创建销毁，本地内存/磁盘不保存跨请求状态——会话上下文丢失、本地缓存失效、数据库连接不能跨请求复用、并发实例无法共享状态。
- **解决（2 分）：**把状态外置到 BaaS——会话存数据库/Redis、临时文件用对象存储；连接改为每次执行新建并配合连接池代理/连接池服务（避免实例过多击穿数据库）；需要共享缓存时使用 Redis 等外部缓存；跨函数长流程用工作流服务编排并持久化中间状态。

### 问题3（8 分）

**（1）四种触发方式（4 分，每种 0.5 分 + 举例 0.5 分）**

| 触发方式 | 适用场景 | 本案例举例 |
|---|---|---|
| API 网关触发 | 同步在线 API 请求 | App 上传运单并同步返回受理结果 |
| 消息队列触发 | 削峰与异步处理，按批拉取消息执行 | 运费结算结果发送后触发计费函数异步落库 |
| 对象存储事件触发 | 文件创建/删除驱动的处理流水线 | 运单照片写入对象存储后自动触发 OCR 识别函数 |
| 定时触发 | 周期性任务 | 每日凌晨定时汇总单据量与费用账单 |

**（2）不适合迁移的特征与本案例取舍（4 分）**

- **不适合（2 分，答出三类）：**长时运行任务（超过单次执行时长上限，如长连接网关、流式计算）；负载平稳且高（FaaS 按量计费反而更贵，且频繁冷启动）；强依赖本地状态/专用硬件（GPU、大内存、文件句柄）或亚毫秒级时延的链路；对启动时延极敏感的核心交易；需强一致复杂事务的长流程。
- **本案例（2 分）：**OCR 识别、计费试算、消息通知、定时报表等短时、事件驱动、波峰波谷明显的环节适合迁移；而面向司机端的高频查询服务（时延敏感、负载平稳）与需要长连接/复杂事务的核心结算服务应保留常驻容器/虚拟机部署，两者经 API 网关/消息队列协同。

## 附二：答题建议

1. **按分值配字数**：25 分大题分 3 问（9/8/8），9 分题约需 8~12 条要点，8 分题约 6~10 条；宁可多写要点，不写大段论述。
2. **概念题先给定义再落地**：凡"说明……的含义""说明……的原理"，先一句话定义，再结合案例补一句"本案例中……"，两点各占一半分。
3. **对比题写"两面"**：要求比较两种方案时，必须写清各自的收益与代价，只写一方只得一半分。
4. **设计模式题写全"模式名 + 意图 + 角色映射"**，只写模式名通常拿不到 2 分以上。
5. **数据类题写过程**：分片键选择、迁移步骤、扩容方案都要写出"为什么"，只写结论会扣分。
6. **时间分配**：90 分钟做 3 题，每题约 28 分钟（读题 5 + 作答 20 + 检查 3）。
