【问题 1】参考答案（8 分）

（1）四个组件职责（每个 1 分，共 4 分）：

  • API Server：集群统一的访问入口，提供 REST API，负责请求的认证、鉴权与准入控制；所有组件（含 kubectl）都通过它读写集群状态，是控制面的通信枢纽。
  • etcd：分布式键值存储，保存集群的全部状态与配置数据，是集群的"唯一事实来源"，需以奇数节点部署保障一致性并定期备份。
  • Scheduler：监听尚未绑定节点的 Pod，依据资源请求、亲和/反亲和、污点容忍等策略为其挑选最合适的节点并完成绑定。
  • Controller Manager：运行各类控制器（Deployment、ReplicaSet、Node、Endpoint 等），通过"期望状态与实际状态对比、不断调谐"的控制循环使集群收敛到期望状态。

（2）作用与关系（共 4 分）：

  • Deployment：声明式管理无状态应用的 Pod 副本（期望副本数、Pod 模板），支持滚动升级与版本回滚，其下层通过 ReplicaSet 管理一组 Pod。（1.5 分）
  • Service：为一组 Pod（按标签选择器圈定）提供稳定的虚拟 IP 与 DNS 名，实现服务发现与四层负载均衡，屏蔽 Pod 的创建销毁与 IP 变化。（1.5 分）
  • Ingress：集群七层入口，按域名、路径规则将外部 HTTP/HTTPS 请求路由到不同 Service，并可完成 TLS 终止。（1 分）
  • 关系：外部流量经 Ingress 规则路由到 Service，再由 Service 转发到后端 Pod；Pod 由 Deployment 创建与保持。即 Ingress → Service → Pod（Deployment 管理）。（1 分）

【问题 2】参考答案（8 分）

（1）工作原理（4 分）：

  • 数据面：向每个业务 Pod 注入一个 Sidecar 代理（如 Envoy），通过流量劫持接管该 Pod 的所有出入流量，在代理中执行服务发现、负载均衡、超时重试、熔断、限流、mTLS 加密与遥测采集；业务容器不感知治理逻辑。
  • 控制面：负责服务发现、路由与策略配置（如 VirtualService / DestinationRule）的下发、证书签发与安全策略管理，通过 xDS 等协议统一配置所有 Sidecar。
  • 即"治理逻辑从业务进程中剥离、下沉到 Sidecar，控制面集中管控、数据面分布执行"。

（2）优点与代价（各至少两点，共 4 分）：

  • 优点：① 语言与框架无关，多语言异构微服务获得一致的治理能力；② 治理策略与业务代码解耦，策略可热更新、网格可独立升级、无需改造或重新发布业务；③ 统一实施 mTLS 身份认证与流量加密，便于零信任落地；④ 统一采集日志、指标与调用链，可观测性好。（2 分）
  • 代价：① 每个 Pod 多一个 Sidecar，带来额外的 CPU/内存开销与一跳网络转发时延；② 引入控制面与 Sidecar 生命周期管理、版本兼容等运维复杂度；③ 调用与排障链路变长，问题定位难度增加。（2 分）

【问题 3】参考答案（9 分）

（1）三种发布策略比较（5 分，滚动、蓝绿、金丝雀每项维度答对给分）：

  • 滚动发布：逐批用新版本替换旧副本，资源开销小；新旧版本共存期风险中等；回滚需反向滚动，速度一般；用户基本无感知，但共存期可能出现行为不一致。
  • 蓝绿发布：新旧两套环境同时在线，资源开销大（接近双倍）；发布前可在绿环境充分验证，风险低；回滚只需把流量切回蓝环境，速度最快；切换瞬间完成、体验好，但可能影响长连接与会话。
  • 金丝雀发布：先引入少量新版本实例按小比例接流量，资源开销小；按比例逐步放量并观察指标，风险最低且可控；异常时灰度权重调回即可回滚，速度快；仅少量用户受影响，体验可控。

（2）策略选择与弹性指标（4 分）：

宜采用金丝雀发布（可辅以蓝绿做大版本切换）。理由：大促峰值流量大且业务核心，按小比例灰度放量可观察错误率、P95 时延、下单成功率等核心指标，风险可控；异常时将灰度权重调整为 0 即可在分钟级完成回滚，满足"5 分钟内回滚"要求；无需长期维持双倍资源，成本可控。（2.5 分）

HPA 可依据的指标：CPU/内存等资源利用率；应用自定义指标（QPS、并发连接数、请求排队长度、消息积压量等，经自定义 Metrics API 接入）；外部业务指标（如下单 TPS）。同时应设置副本数上下限与缩容冷却窗口，配合 PodDisruptionBudget 保证缩容期间的服务能力。（1.5 分）

【问题 1】参考答案（8 分）

（1）三个基本假设及失效原因（4 分，假设每个 1 分，结合案例 1 分）：

  • 假设：① 内网是可信的，只有外网不可信（"城堡与护城河"）；② 用户/终端一经认证即可长期信任（一次认证、长期授权）；③ 终端与业务系统属于企业物理边界内，位置固定、设备可控。
  • 失效原因：远程办公与移动办公使访问点不再位于边界内，"内网"边界消失；多云与跨云调用使业务资源与流量路径都在企业边界之外；第三方人员与 BYOD 终端不可控。案例中两起事件正是上述假设失效的体现——合法账号（一次认证）获得隧道后即可被无信任横向移动、失控终端复用既有隧道进入内网。

（2）核心思想与两项技术（4 分）：

  • 零信任核心思想："永不信任、始终验证"——不以网络位置作为信任依据，每次访问都基于身份、设备与环境的组合进行认证与授权，遵循最小权限并持续评估、动态调整；默认假设网络已被攻破。（2 分）
  • SDP：以"先认证、后连接"的方式对外隐藏业务资源（默认拒绝、单包授权），使未授权者看不到也连不上资源，解决资源暴露面问题。（1 分）
  • 微隔离：在数据中心/云内部按工作负载划分安全域并实施东西向最小权限访问控制，阻断入侵后的横向移动。（1 分）

【问题 2】参考答案（9 分）

四个方面各 2—3 分（能力 1 分 + 措施每项 0.5—1 分）：

  • 身份可信：建设统一身份目录与 SSO，单点登录（OIDC/SAML）；全面启用多因素认证 MFA；特权账号集中托管（堡垒机）与双人复核；凭证短期化并定期轮换。（约 2.5 分）
  • 设备可信：终端准入控制（NAC/802.1X），未注册设备禁止接入；EDR 检测 + 补丁与基线安全核查，设备健康状态不达标则降权或引导至修复区；设备指纹绑定，防账号盗用。（约 2 分）
  • 权限最小化：按"应用 + 操作"而非按网段授权；RBAC 叠加 ABAC（依据部门、时间、地理位置、设备状态动态计算权限）；敏感操作 JIT 临时授权并审批；默认拒绝一切未显式授权的访问。（约 2.5 分）
  • 持续监测与响应：集中采集访问日志与全流量日志（满足等保三级审计要求）；UEBA 建立基线，发现异地登录、非工作时间批量查询等异常即提升风险等级；自适应策略——风险升高时要求二次认证、缩权或阻断，并对高危会话全程录制回溯。（约 2.5 分）

【问题 3】参考答案（8 分）

（1）OAuth 2.0 四种授权模式（每种 1 分，共 4 分）：

  • 授权码模式（Authorization Code，可配合 PKCE）：最完整安全，适用于有后端的 Web 应用与移动 App，令牌由后端以授权码换取。
  • 隐式模式（Implicit）：令牌直接经前端返回，历史上用于纯前端单页应用，现已不推荐。
  • 密码模式（Resource Owner Password Credentials）：用户直接把账号密码交给客户端，仅适用于高度信任的自有客户端或遗留系统迁移。
  • 客户端模式（Client Credentials）：无用户参与，适用于服务之间的机器对机器（M2M）调用，如本案例跨云服务间调用。

（2）OIDC、JWT 与安全注意（4 分）：

  • 关系：OIDC 是构建在 OAuth 2.0 之上的身份认证层——OAuth 2.0 只解决"授权"，OIDC 引入 ID Token（JWT 格式）、UserInfo 端点与标准 scope，解决"认证用户是谁"的问题。（1.5 分）
  • 结构：JWT 由头部（签名算法与类型：alg、typ）、Payload（声明 claims）、Signature（对前两段的签名）三段组成，分别 Base64URL 编码后以"."连接。（1 分）
  • 注意事项（答出两个即可，每个 0.75 分）：① Payload 仅编码而非加密，不得放置敏感信息；② 必须校验签名并固定允许的算法，防"alg=none"与算法混淆攻击，同时校验 iss/aud/exp；③ JWT 签发后难以主动吊销，应设置较短有效期并配合 Refresh Token 与黑名单/网关拦截；④ 避免令牌出现在 URL 中造成日志泄露。

（1）三类实时系统（2 分）与判断（1 分）：

  • 硬实时：必须在截止期内完成，超时结果无效并可能造成严重后果（人身伤害、重大损失）；

  • 本系统控制周期 1 ms，超时可能导致机械臂伤人，属硬实时系统。

U = C1/T1 + C2/T2 + C3/T3 = 1/4 + 2/8 + 2/16 = 0.25 + 0.25 + 0.125 = 0.625　（2 分）

【问题 2】参考答案（8 分）

（1）WCET 意义（2 分）与平均时间不可用的原因（1 分）：

  • WCET 是任务在最坏执行路径与最坏运行条件（缓存、流水线、总线竞争）下的执行时间上界，是调度性分析与保证截止期的依据；安全相关系统必须按最坏情况设计并预留余量。
  • 平均执行时间只反映统计均值，实际运行可能超出均值数倍，一旦超出即造成任务超期；硬实时系统的每次超时都不可接受，故不能以平均值判定可调度性。

（2）时间隔离与空间隔离（各 1.5 分）：

  • 时间隔离：为各任务/分区分配确定的执行时间窗口，由分区调度器保证某分区超时或故障时不侵占其他分区的 CPU 时间（如 ARINC 653 的时间分区调度），使故障影响被限制在分区内。
  • 空间隔离：通过 MPU/MMU 为各分区划定私有内存与只读代码段，限制其可访问地址空间，防止越界读写破坏其他分区数据，实现故障的内存级隔离。

（3）看门狗（2 分）：

  • 作用：独立于主程序的定时器，程序须周期性"喂狗"；程序死循环、跑飞而未按时喂狗时触发超时复位，使系统从软件故障中自动恢复到已知状态（fail-safe）。
  • 区别：普通看门狗只检测"到期未喂狗"；窗口看门狗要求喂狗落在设定的时间窗口内，喂狗过早（程序异常、跳步）或过晚都会触发复位，可检测程序执行时序的异常。

【问题 3】参考答案（8 分）

（1）2oo3 表决（4 分）：

  • 原理：三路独立通道采集同一物理量，表决器取"多数一致"的值作为输出；任意一路故障时仍有另两路正确值，系统继续正常运行并定位故障通道。（2 分）
  • 优势：相对单通道无容错能力，任一故障即出错；相对双通道，当两路结果不一致时无法判别哪一路错误、只能停机，2oo3 在容忍单路故障的同时保证系统不停机，可靠性高、可用性优于双通道。（1 分）
  • 局限与防范：对共因故障无效（三路若共用电源、时钟、安装位置或同一软件版本，同一原因会导致多路同时失效），故应采用技术多样性（不同原理/厂商的传感器）、物理与电气隔离、独立供电与独立软件版本等防范措施。（1 分）

（2）心跳、切换时间与安全通道（4 分）：

  • 心跳用于主备机互相探测存活；周期状态同步将主机的控制状态（当前轨迹、积分项、I/O 状态等）同步到备机，使备机始终处于"热"态，切换后无需从零重建控制。（1.5 分）
  • 若切换瞬间（心跳检测超时 + 状态恢复 + 输出接管）超过 1 ms 控制周期，将造成控制周期输出缺失，引起机械臂抖动甚至失稳；因此须缩短心跳周期、采用输出比对/并行输出等机制缩短接管时间。（1.5 分）
  • 主备可能同时失效或因共因失效一起失效，控制系统不能既当"运动员"又当"裁判员"；独立的安全状态输出通道（安全继电器、STO 安全转矩关断）在检测到危险时直接切断动力输出，保证系统进入确定的机械安全状态，构成"控制 + 保护"相互独立的双通道。（1 分）

【问题 1】参考答案（9 分）

（1）三种模式比较（6 分，每种模式每答对一个维度给分）：

  • 独立数据库：隔离性最强（数据、备份、加密、故障域完全独立，易满足合规）；成本最高（每租户一套实例，资源利用率低）；可按租户独立扩容与迁移；运维复杂（备份、升级、监控随租户数线性增长）。
  • 共享库独立 Schema：隔离性较高（同库不同 Schema，权限可分离，但共享实例资源）；成本居中；单库 Schema 数量与跨 Schema 统计限制了扩展性；运维较简单，可统一升级。
  • 共享表 + 租户标识（Tenant_ID）：隔离性最低，完全依赖应用层过滤与旁路；成本最低、资源利用率最高；最利于水平分库分表扩展；运维最简单，但单表数据量大、热点集中。

（2）分层方案（3 分）：

采用分层混合：8 家大客户用独立数据库（满足数据独立存储、定制报表与合规要求）；中等规模租户用共享库独立 Schema；大量小微租户用共享表 + Tenant_ID（成本最优）。

通过统一的"数据访问路由层（按租户 ID 查询路由配置）"屏蔽底层差异，使上层业务代码对隔离模式无感知；租户规模变化时可在模式间迁移。

【问题 2】参考答案（8 分）

（1）租户上下文（3 分）：

  • 接口层对资源做归属二次校验（防 IDOR 越权访问）；所有访问记录含租户标识的审计日志。

（2）退租处置与吵闹邻居（4 分）：

  • 退租处置：提供标准格式的数据导出；按合同约定保留期届满后彻底删除（共享表按 tenant_id 批量物理删除，并覆盖备份介质中的残留）；销毁该租户密钥；出具数据删除证明，满足《个人信息保护法》《数据安全法》的删除权与安全要求。（2 分）
  • 吵闹邻居治理：按租户限流与配额（见问题 2）；大租户独立实例/独立分片或独立线程池与队列隔离；连接池、资源组按租户隔离；慢查询与长事务治理，按租户监控告警，必要时将热点租户平滑迁移到独立资源。（2 分）
