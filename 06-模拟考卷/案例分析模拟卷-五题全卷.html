【问题3】（8 分）敏感点与权衡点

架构组在评估会上提出如下架构决策：

"结算核心采用两地三中心 + 同步复制方案：生产中心与同城灾备中心同时对外提供服务，结算数据同步写入两地，保证任一中心故障时数据零丢失。但同步复制使单笔结算平均写入延迟由 45ms 增加到 130ms；同时为满足 30 年留痕要求，所有结算表开启全量审计日志，进一步使写入 TPS 下降约 18%。"

问题 1（8 分）质量属性归类

  • 性能 (1)：a、g
  • 安全性 (2)：b、e、f
  • 可用性 (3)：c、f

问题 2（9 分）质量属性效用树

  • (1) 性能（下挂 a、c 两个性能场景）
  • (2) 可用性（下挂 (4) 与 g）
  • (3) f（安全性分支下的"攻击时保核心可用"场景）
  • (4) c（可用性分支下的"主节点故障 30 秒切换"场景）
  • (5) d、(6) h（可修改性分支）

采分点：(1)(2) 各 1.5 分，四个场景空各 1.5 分。易错：把 g（登录并发响应 2 秒）误归入可用性——它本质是性能；(3) 处填 c 不填 f，因为 f 是"攻击下保可用"，放安全性分支更贴切。

问题 3（8 分）敏感点与权衡点

  • 敏感点："两地三中心 + 同步复制"这一决策。
    理由：它显著影响可用性（任一中心故障数据零丢失）与性能（写入延迟 45ms→130ms），是实现某质量属性的关键架构决策。
  • 权衡点：同一决策同时影响多个质量属性且方向相反——提升可用性/可靠性（零丢失、快速切换），但降低性能（延迟增至近 3 倍、TPS 降 18%）。
    理由：权衡点的本质是"提升 X 但降低 Y"，此处 X=可用性，Y=性能。
  • 风险点（任答 1 个即可）：
    1. 同步复制受跨中心网络时延制约，若两地链路抖动可能导致主中心写入被阻塞，反而放大可用性风险；
    2. 全量审计日志在高并发下可能撑爆存储与 IO，且 30 年留痕的数据归档、检索方案尚未验证；
    3. 同步复制 + 审计日志双重放大写入压力，月末高峰 QPS 1.2 万时可能出现写队列积压。

采分点：敏感点 2 分、权衡点 2 分、理由各 1.5 分、风险点 1 分。关键区分：敏感点只需指出"影响某个质量属性的关键决策"；权衡点必须体现"同时影响多个质量属性且有正有负"。只写"这是敏感点也是权衡点"而不给理由不得分。

本大题围绕架构风格对比、选型论证与构件设计展开，共 3 个小题。
【说明】

某装备制造企业拟建设"工业物联网设备管理平台"，接入 12 万台数控机床与传感器，提供设备状态监控、故障预警、能耗分析、远程运维四大能力。平台数据流大致为：设备采集 → 协议解析 → 数据清洗 → 特征提取 → 规则/模型判断 → 告警与存储。

两类业务需求差异明显：

  • 实时监控类：设备振动、温度、电流持续上报（合计约 40 万点/秒），要求端到端延迟 ≤ 500ms，超阈值立刻告警；
  • 离线分析类：每晚对全量历史数据做能耗统计与设备健康度建模，单次处理 TB 级数据，允许小时级延迟。

  • 方案 A（批处理风格）：数据先全量落盘，定时调度批作业统一处理，处理完再输出结果；
  • 方案 B（管道-过滤器风格）：各处理环节封装为过滤器，数据流经管道逐段处理，边到边输出。

此外，现场协议极其混杂：Modbus、OPC UA、Profinet、MQTT、自定义串口协议共存；且企业要求未来新增协议时不影响已有解析逻辑。

问题 2（9 分）选型论证

(1) 实时监控类 → 管道-过滤器风格（3 分），理由（每点 1 分，答 3 点得 3 分）：

  • 时延匹配：要求端到端 ≤ 500ms，管道-过滤器流式处理天然满足；批处理必须等整批就绪，无法满足秒级要求。
  • 持续输入：40 万点/秒持续上报，数据永无"全部就绪"的时刻，批处理前提不成立。
  • 及时告警：超阈值须立刻告警，流式处理可在"规则判断"过滤器即时触发，无需等待整批。
  • 热路径可扩展：数据清洗、特征提取是算力热点，可对单个过滤器独立扩容。

(2) 离线分析类 → 批处理风格（2 分），理由：

  • TB 级历史数据、允许小时级延迟，批处理可做全量扫描与全局聚合，统计口径更准确；
  • 批处理对资源占用可安排在夜间低谷，成本更优。

(3) 整体结论（1 分）：采用"管道-过滤器（实时链路）+ 批处理（离线链路）"并存的双链路架构，

  • 实时链路：设备 → 协议解析 → 清洗 → 特征提取 → 规则判断 → 告警（毫秒级）；
  • 离线链路：原始数据落数据湖 → 夜间批作业做能耗统计与健康度建模；
  • 两链路通过统一数据落地层（消息队列 + 对象存储/数据湖）解耦，实时链路把原始数据旁路写入，离线链路只读。

易错点：① 只答一种风格而忽略第二类业务，最多得 4 分；② 选批处理做实时监控直接判错；③ 不引用题干数字（500ms、40 万点/秒、TB 级）视为空泛论述，扣 1—2 分。

问题 3（8 分）构件设计

(1) 实时链路关键构件（5 分，每个 1 分，职责说清即可）：

  1. 设备接入/采集构件：建立与机床、传感器的连接，持续拉取或接收上报数据；
  2. 协议解析过滤器：将 Modbus / OPC UA / Profinet / MQTT / 串口等原始报文解析为统一内部数据模型；
  3. 数据清洗过滤器：处理缺失值、异常值、时间戳对齐、去重；
  4. 特征提取过滤器：计算滑动窗口统计量（均值、方差、峰值、频域特征）；
  5. 规则/模型判断过滤器：与阈值或模型比对，判定是否异常；
  6. 告警生成与通知过滤器：生成告警事件并推送短信/企业微信/工单系统；
  7. 数据输出过滤器：分流写入时序库（实时指标）与数据湖（原始数据，供离线链路）。

(2) 协议扩展方式（3 分）：

  • 管道-过滤器的本质是过滤器接口统一、可插拔。为每种协议实现一个独立的协议解析过滤器，统一实现同一输入输出契约（原始报文 → 内部数据模型）；
  • 新增协议时只需新增一个过滤器实现并注册到管道，通过配置或路由把该协议的数据导向对应过滤器，已有过滤器代码零改动——这正是"新增协议不影响已有解析逻辑"的落点；
  • 用到的设计模式：策略模式（不同协议解析算法可互换）、工厂模式（按协议类型创建解析器）、适配器模式（把异构协议适配为统一模型）；若答责任链模式（过滤器串联）亦可。

采分点：构件 5 分 + 扩展方式 2 分 + 设计模式 1 分。易错：只列构件名不说职责，每个扣 0.5；设计模式乱答（如答"单例模式"）不得分。

问题 1（8 分）范式判定与分解

(1) 判定（3 分）：

  • R1 最高满足 1NF（2 分）。理由：主键为 (订单号, 商品编号)，但存在部分函数依赖——订单号 → 门店编号/收银员编号/会员编号，商品编号 → 商品名称/单价，都只依赖主键的一部分；此外门店编号 → 门店名称/地址、收银员编号 → 收银员姓名、会员编号 → 会员等级为传递依赖。
  • R2 满足 3NF（1 分）。理由：主键 (门店编号, 商品编号)，库存数量/安全库存/补货周期完全函数依赖于整个主键，且不存在传递依赖。

(2) R1 规范化为 3NF（5 分，每个正确模式 1 分）：

门店(门店编号 PK, 门店名称, 门店地址)

问题 2（9 分）反规范化与读写分离

(1) 为何还要反规范化（4 分）：

  • 3NF 消除冗余带来更多的表和连接（JOIN），一次商品详情查询可能涉及商品、库存、门店、促销 4—5 张表；在 8000 QPS 下，多表 JOIN 无法满足 50ms 响应要求。（1 分）
  • 具体反规范化设计（2 分，任答 1 个）：
    1. 在"商品"表中冗余"当前库存数量""门店名称"字段，把详情页查询从多表 JOIN 降为单表查询；
    2. 在"订单明细"中冗余"商品名称""单价快照"（下单时价格固化），既避免关联商品表，也保证历史单据价格不随商品调价而变；
    3. 建宽表/物化视图，把商品+库存+促销预拼成一张查询表，由异步任务刷新。
  • 代价（1 分）：引入数据冗余与不一致风险——同一数据多处存储，更新需同步多处；若用异步刷新，会存在短暂数据窗口不一致（如库存显示滞后）。

(2) 读写分离的问题（3 分）：

  • 主从复制延迟（1 分）：写主库后立即查从库，可能读到旧数据（如"下单成功但订单列表查不到"），即读己之写一致性被破坏。
  • 应对措施（2 分，每条 1 分，答 2 条）：
    1. 强制走主库：对实时性要求高的读写（如支付后立即查订单、库存扣减后校验）标记为走主库；
    2. 半同步复制：保证至少一个从库确认收到 binlog 后才返回写成功，压缩延迟窗口；
    3. 延迟感知路由：监控从库延迟，超过阈值（如 200ms）自动把该查询切到主库；
    4. 会话粘滞：同一会话内写后的读固定路由到主库一小段时间。

(3) 除缓存外降压手段（2 分，每条 1 分）：

  • 限流与排队：网关层对单商品维度限流，超阈值排队或返回兜底；
  • 静态化/预计算：商品详情页静态化或预生成，甚至用 CDN 承载；
  • 读写分离 + 从库横向扩容，把读压力分摊到多从库；
  • 连接池与 SQL 优化：合理连接池大小、覆盖索引避免回表；
  • 本地缓存 + 多级缓存：JVM 本地缓存扛住热点单品（如 Caffeine）。

采分点：(1) 4 分 (2) 3 分 (3) 2 分。易错：说"反规范化就是加索引"——加索引不是反规范化；说"读写分离能解决延迟"而不说主从延迟问题，属答偏。

问题 3（8 分）NoSQL 选型

(1) 类型选择与理由（4 分）：

应选列式（宽列）数据库或文档型数据库为主的 NoSQL。理由（每点 1 分，答 3 点）：

  • Schema 灵活：字段不固定且持续新增，关系库改表代价高，NoSQL 天然 schema-less；
  • 写多读少、只追加：日均 12 亿条写入，列式/文档库的追加写吞吐远高于关系库；
  • 水平扩展：数据量持续增长，NoSQL 可线性增加节点（分区/分片）；
  • 稀疏列存储高效：埋点字段大量空缺，列式存储可只存非空列，压缩率高。

(2) 候选产品（2 分，每个 1 分）：

  • HBase：基于 HDFS、强一致、适合海量稀疏数据的随机读写，与大数据生态（Spark/Flink）天然集成，适合后续离线分析；
  • MongoDB：文档模型、schema 灵活、开发友好，适合结构多变的埋点与快速迭代；
  • ClickHouse（补充）：列式 + 极高压缩与聚合性能，适合埋点的实时多维分析（偏 OLAP）。

(3) 局限与应对（2 分）：

  • 局限：NoSQL 通常不支持复杂 JOIN 与跨行事务，且不擅长大范围聚合分析（HBase/MongoDB 尤其）；
  • 应对：把埋点数据同时写入数据湖/OLAP 引擎（如 ClickHouse、Hive/Doris）承载分析场景，形成"线上查询用 NoSQL、分析用 OLAP"的双写或异步同步；对需要关联的维度（商品、门店）在写入时打宽/预关联，避免运行时 JOIN。

采分点：类型+理由 4 分 + 产品 2 分 + 局限与应对 2 分。易错：答"Redis"——Redis 是缓存/键值存储，不适合存 12 亿条需要持久化与分析的埋点；只写产品名不写适用点扣分。

问题 1（8 分）可靠性指标计算

(1) 串联可用性（3 分）：

A_串 = 0.9995 × 0.9990 × 0.9998
     = 0.9995 × 0.9990 = 0.9985005
     × 0.9998 ≈ 0.99830080
即 ≈ 99.8301%

(2) 单机可用性（2 分）：

A = MTBF / (MTBF + MTTR) = 2000 / (2000 + 4) = 2000/2004 ≈ 0.998004 ≈ 99.8004%

(3) 主备并联可用性（3 分）：

A_并 = 1 − (1 − A)² = 1 − (1 − 0.998004)²
     = 1 − (0.001996)² ≈ 1 − 0.000003984
     ≈ 0.99999602 ≈ 99.9996%

问题 2（9 分）容灾等级与 RTO/RPO 设计

(1) RTO 与 RPO（3 分）：

  • RTO（恢复时间目标）= ≤ 30 分钟：灾难发生后，业务从中断到恢复可用的最长可接受时间；
  • RPO（恢复点目标）= 0（零丢失）：灾难发生时，允许丢失的数据时间跨度；RPO=0 表示任何已提交数据都不允许丢失；
  • 区别（1 分）：RTO 衡量"恢复多快"（时间维度，关注业务中断时长），RPO 衡量"丢多少数据"（数据维度，关注数据完整性）。

(2) 容灾等级（3 分）：

  • 要达到 RPO = 0，至少需要达到数据级容灾中的最高等级——第 6 级（数据零丢失），即远程数据同步复制 + 自动切换的容灾能力；
  • 理由：只有同步复制（写主中心成功前必须确认灾备中心已收到并落盘）才能保证 RPO=0；异步复制必然存在复制延迟，灾难瞬间会丢失延迟窗口内的数据，RPO>0。同时 RTO ≤ 30 分钟要求具备自动/半自动切换能力，人工切换通常无法在 30 分钟内完成。
  • （若按"两地三中心"等级体系作答，答"同城双活 + 异地灾备/同步复制"亦可给分。）

(3) 方案设计与代价（3 分）：

  • 布局：两地三中心——同城双中心（生产中心 A + 同城灾备中心 B，光纤直连、时延 <2ms）+ 异地灾备中心 C（跨城，约 1000km）；
  • 复制方式：同城 A↔B 采用同步复制（保证 RPO=0），异地 C 采用异步复制（规避长距离同步导致的写阻塞）；
  • 切换：同城故障由负载均衡 + 数据库自动主备切换（RTO 秒级至分钟级）；同城整体灾难时切换至异地 C，通过 DNS/GSLB 引流（RTO 控制在 30 分钟内）；
  • 成本代价（1 点即可）：① 资源成本约为单中心的 3 倍（三套机房 + 带宽）；② 同步复制使写延迟增加（同城约 +5—20ms）；③ 跨中心数据一致性校验、灾备演练与运维复杂度显著上升。

采分点：(1) 3 分 (2) 3 分 (3) 3 分。易错：把 RTO 与 RPO 说反；认为"异步复制也能做到 RPO=0"（这是典型错误）；只说"上云/多活"而不给复制方式与切换手段。

问题 3（8 分）限流、熔断与降级

(1) 三者区别与实例（3 分，每项 1 分）：

手段作用本题实例
限流主动限制入口流量速率，防止超出系统处理能力在出款网关入口按商户维度做令牌桶限流，如单商户 500 TPS，超出返回"请稍后重试"

(2) 熔断器设计要点（3 分，每点 1 分）：

  • 隔离配套：按下游银行通道分别设置熔断器（舱壁隔离），单通道故障不影响其他通道。

问题 1（7 分）微服务拆分

(1) 拆分原则（3 分，每条 1 分，答 3 条）：

  • 单一职责 / 业务能力单一：一个服务只负责一个业务能力，对应一个可独立演进的业务域；
  • 高内聚低耦合：强相关的功能放同一服务，服务间通过明确定义的接口通信，减少跨服务调用链；
  • 按业务能力/子域拆分（而非按技术分层）：不拆成"controller 服务 / dao 服务"，而是按订单、库存等业务域拆；
  • 数据私有：每个服务独占自己的数据库/Schema，禁止跨服务直接读对方表；
  • 与组织结构对齐（康威定律）：服务边界尽量与团队边界一致；
  • 可独立部署与演进：服务应能被单独开发、测试、发布、扩缩容；
  • 适度粒度：避免"分布式单体"（拆得过细导致调用链过长）与"拆得过大"。

(2) 限界上下文与微服务边界（2 分）：

  • 限界上下文（Bounded Context）是 DDD 中对领域模型的边界划分，在同一上下文内，领域术语（如"商品"）有唯一、明确的含义；
  • 限界上下文是微服务边界的首要依据——通常一个限界上下文对应一个（或一组）微服务，因为上下文内部模型高度内聚、上下文之间需通过明确的契约（上下文映射）通信；
  • 注意：二者并非严格 1:1，一个上下文可能拆成多个服务（按伸缩特性），多个小上下文也可能合并为一个服务（避免过度拆分）。

(3) 拆分结果与不宜拆分处（2 分）：

  • 拆分结果：用户服务、商品服务、购物车服务、订单服务、库存服务、支付服务、优惠券服务、物流服务、评价服务；
  • 需谨慎拆分（1 分，任答 1 个）：
    1. 订单与订单明细不应拆开——它们是同一限界上下文，强一致、同事务，拆开会导致跨服务事务；
    2. 库存与商品可保持较近的边界或同库——库存扣减需与 SKU 强一致校验；
    3. 支付不宜过度拆分为"支付单/支付流水/对账"多个服务——支付是资金强一致域，且需与外部渠道对接，过度拆分放大一致性风险；
    4. 评价/物流虽可独立，但与主交易链路耦合低，应异步解耦而非同步调用。

采分点：原则 3 分 + 限界上下文 2 分 + 拆分结果与理由 2 分。易错：按"controller/service/dao"技术分层拆分（判错方向）；只说"按业务拆"不解释限界上下文与边界关系。

问题 2（6 分）缓存三大问题

(1) 三者含义与区别（3 分，每项 1 分）：

问题含义区别关键
缓存穿透查询的 key 在缓存和数据库中都不存在，请求每次都打到数据库数据根本不存在
缓存击穿某个热点 key 突然过期，瞬间大量并发请求同时打到数据库单个热点 key 失效
缓存雪崩大量 key 在同一时刻集中过期，或缓存集群整体宕机，导致请求全部涌向数据库大量 key 同时失效 / 缓存层整体不可用

(2) 解决方案（2 分，答出对应即可）：

  • 穿透：① 布隆过滤器前置拦截不存在的 key；② 对空结果也缓存（空值缓存，设短 TTL）；③ 接口层参数校验拦截非法 key。
  • 击穿：① 热点 key 逻辑过期（不设物理 TTL，异步刷新）；② 互斥锁/分布式锁保证只有一个线程回源重建缓存；③ 热点数据预热 + 永不过期。
  • 雪崩：① TTL 加随机抖动，避免集中过期；② 缓存高可用集群（哨兵/集群模式）+ 多级缓存；③ 熔断降级限流保护数据库；④ 缓存预热。

(3) 爆款 SKU 8 万 QPS 属于哪个问题（1 分）：

属于缓存击穿（热点 key 失效瞬间被打穿）。因为该 key 对应的数据确实存在（排除穿透），且是单个热点 SKU（排除雪崩的多 key 同时失效）。
应对首选：逻辑过期 + 互斥锁重建，并配合热点数据预热、本地缓存（Caffeine）扛住热 key。

采分点：三者辨析 3 分 + 方案 2 分 + 判断 1 分。易错：把击穿与雪崩混为一谈；把"爆款商品"判成雪崩。

问题 3（6 分）库存一致性

(1) Cache Aside 仍可能不一致的情形（2 分）：

  • 并发时序错乱：线程 A 读缓存未命中 → 查库得旧值 → 此时线程 B 更新数据库并删除缓存 → A 再把旧值写回缓存，导致缓存长期是旧值（"先删后写回"的经典竞态）；
  • 删除缓存失败：更新 DB 成功后删缓存失败（网络/超时），缓存仍是旧值，直到 TTL 过期；
  • 主从延迟：写主库后立即删缓存，但读请求从从库读到旧值又写回缓存；
  • 读写并发下的中间态：扣减库存这类"读改写"操作，若不加原子控制，缓存与 DB 的中间状态会被并发读到。

(2) 防超卖 3 种手段及优缺点（3 分，每种 1 分）：

手段优点缺点
数据库行锁 / 悲观锁（SELECT … FOR UPDATE）强一致，实现简单热点行锁竞争剧烈，吞吐低，易超时/死锁
乐观锁（版本号 / CAS）无阻塞，读多写少时性能好高冲突下大量更新失败需重试，热点商品重试率高
Redis 原子扣减（DECR / Lua 脚本）原子、高并发性能极好，可挡在 DB 之前需处理与 DB 的最终一致（异步落库、对账补偿）
（补充）库存分段、消息队列串行化分散热点 / 削峰复杂度高，分段需聚合

(3) 爆款场景选型（1 分）：

应选 Redis 原子扣减（Lua 脚本）+ 库存分段 + 异步落库 + 对账补偿。

理由：8 万 QPS 打 2000 件库存，数据库行锁必然被打爆；Redis 单线程原子操作可承受高并发，Lua 脚本保证"查库存+扣减"原子执行；库存分段可进一步分散单 key 热点；扣减成功后再通过消息队列异步落库，并用定时对账兜底最终一致。

采分点：(1) 2 分 (2) 3 分 (3) 1 分。易错：只说"加锁"不区分场景；在 8 万 QPS 场景选数据库悲观锁（实际不可行）。

问题 4（6 分）分布式事务方案

(1) 三种方案原理与差异（3 分，每种 1 分）：

方案原理适用/特点
2PC协调者先发 prepare，各参与者锁定资源并投票；全部同意后发 commit，否则 rollback强一致、实现相对简单；但同步阻塞、协调者单点、性能差，不适合高并发长事务
TCC每个服务实现 Try（预留资源）、Confirm（确认）、Cancel（释放）三接口，由业务补偿最终一致、性能好、可跨长流程；但业务侵入大，需自行保证幂等与悬挂/空回滚
本地消息表本地事务内写业务数据 + 消息表；异步投递 MQ，消费方幂等处理，失败重试最终一致、可靠、无阻塞；但存在延迟，需消息表与对账兜底

(2) 本平台选型（1 分）：

选最终一致性方案（本地消息表 / 可靠消息 + Saga/TCC 补偿），而非 2PC。

理由：下单是高并发短流程（15 万 QPS），2PC 的同步阻塞与全局锁会在热点商品上直接打爆；且下单链路跨 4 个服务，要求"下单不阻塞、失败可补偿"，最终一致 + 幂等 + 对账更契合电商场景。对资金相关的支付步骤可局部采用 TCC 保证更严格的一致性。

(3) 幂等与补偿（2 分）+ 缺陷（见下）：

  • 不重复扣减：为每次下单生成全局唯一业务流水号（幂等键），库存与优惠券的扣减记录以该流水号为唯一索引；消费方处理前先查该流水号是否已处理（或插入唯一约束，冲突即视为重复并丢弃）；同时用 Redis 记录幂等状态防并发重复。
  • 失败补偿：扣减动作都记"预扣/冻结"状态，订单最终成功则确认，失败或超时则释放（回滚）；靠定时任务 + 对账扫描"悬而未决"的中间态（如库存已扣但订单未创建），按超时规则自动补偿，并保留人工干预入口。
  • 已知缺陷：① 存在短暂的数据不一致窗口（用户可能看到"已下单"但库存尚未最终落库）；② 补偿逻辑复杂，若补偿本身失败会留下脏数据，必须依赖对账兜底；③ 消息重复投递需幂等严格保障，否则仍可能重复扣减。

采分点：(1) 3 分 (2) 1 分 (3) 2 分。易错：在高并发场景一味选 2PC；谈最终一致却不说幂等键与补偿对账，只答"用 MQ"不得分。
